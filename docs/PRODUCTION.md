# Production-требования SABR

`docker-compose.yml` воспроизводит всю инфраструктуру на одном компьютере и предназначен для разработки и приёмочного тестирования. Публичное production-развёртывание использует те же контейнеры и контракты, но не должно публиковать базы данных, Redis, RabbitMQ, MinIO Console или внутренние API напрямую в интернет.

## Обязательные меры перед публичным запуском

1. Создать `.env` из `.env.example`, сгенерировать уникальные длинные значения для каждого секрета и хранить их в secret manager CI/CD, а не в Git.
   Для витрины и админки отдельно задать публичные build-time значения из `frontend/.env.example` и `admin-frontend/.env.example`. При сборке админки через Compose используются `ADMIN_AUTH_API_URL`, `ADMIN_CATALOG_API_URL`, `ADMIN_ORDERS_API_URL` и `ADMIN_MEDIA_API_URL` из корневого `.env`.
2. Поставить reverse proxy/load balancer с TLS. Публичными оставить только storefront, необходимые клиентские API и read-only media-домен. Админку разместить на отдельном домене за VPN, identity-aware proxy или сетевым allowlist.
3. Убрать наружные порты PostgreSQL, Redis, RabbitMQ, MinIO Console и внутренних сервисов; разрешить сетевое взаимодействие по allowlist.
4. Разделить роли и учётные данные PostgreSQL по сервисам. Пользователь media-сервиса уже ограничен bucket `sabr-product-media`.
5. Хранить MinIO минимум на нескольких дисках/узлах с erasure coding либо заменить endpoint на управляемое S3-совместимое хранилище. Настроить versioning, lifecycle и резервное копирование.
6. Настроить регулярные проверяемые backup/restore для каждой PostgreSQL БД и MinIO; резервная копия без теста восстановления не считается готовой.
7. Добавить централизованные структурированные логи, метрики, трассировку, Sentry/аналог, алерты по health checks и заполнению дисков.
8. Ограничить размер HTTP-запроса на reverse proxy. `media-api` дополнительно ограничивает файл 12 МБ, проверяет реальный формат/разрешение, удаляет метаданные и перекодирует изображение в WebP.
9. Запускать миграции отдельной release-задачей перед rollout, а не одновременно из нескольких реплик приложения.
10. Настроить rolling deployment, readiness/liveness probes, resource limits, rate limits и автоматический rollback.

## Административный доступ

- Перед первым запуском задать `ADMIN_PHONE` реальным контролируемым номером. Bootstrap только создаёт или активирует этого администратора и не публикует endpoint для повышения роли.
- После первичной инициализации можно задать `ADMIN_PHONE=` пустым значением, чтобы отключить bootstrap. Снятие роли у прежнего администратора выполняется отдельной контролируемой операцией, а не сменой переменной.
- В production запрещён `SMS_PROVIDER=mock`: нужен реальный SMS-провайдер, ограничения частоты на reverse proxy и мониторинг подозрительных входов. Для административных аккаунтов следующим усилением должна стать MFA, не зависящая только от SMS.
- Разрешённые CORS origin и CSP в `admin-frontend/nginx.conf` должны содержать только реальные HTTPS-домены deployment. Локальные адреса из Docker-сборки нельзя переносить в публичную конфигурацию.
- Access token хранится только в памяти вкладки, refresh token остаётся в `HttpOnly` cookie. Серверная проверка роли обязательна для каждого административного маршрута; скрытие кнопок в React не является защитой.

## Хранение изображений

- Оригинальный входной файл не становится публичным: `media-api` декодирует его и создаёт нормализованный WebP.
- PostgreSQL хранит `object_key`, alt-текст и порядок изображения; бинарные файлы находятся только в MinIO/S3.
- Для витрины bucket доступен на чтение. Внешняя запись запрещена; загрузка и удаление проходят через access token администратора.
- `MEDIA_PUBLIC_BASE_URL` позволяет поставить CDN или отдельный media-домен без миграции строк в БД.
- При удалении товара сначала меняется состояние каталога, а физическое удаление объекта выполняется после проверки ссылок и с возможностью отложенного восстановления. Админка будет следовать этому правилу.
